# RH-W-19: External Root of Trust and Dual Implementation Route

## The Limits of Self-Certification

SHA-256 can answer "whether a file matches its index," but it cannot independently answer:

- Who published the index;
- Whether the verifier is correct;
- Whether the generator and verifier share the same error;
- Whether the entire package was replaced after release.

## Recommended Trust Upgrades for Batch 02

### Layer 1: Signed release manifest

Create an offline signature for the release manifest. The website only publishes the signature, commit, and ZIP digest, keeping the private key out of the research toolchain.

### Layer 2: Reproducible builds

Reconstruct the certificate from a fixed source, fixed Python version, and dependency lockfile, requiring that two builds produce the same canonical JSON digest.

### Layer 3: Independent verifier

Implement at least one verifier in a different language or with a different arithmetic backend, such as:

- Python `Fraction` verifier;
- Rust big-rational verifier;
- A small kernel checker generated by Lean.

### Layer 4: External mirrors

Simultaneously publish the digest on the website, GitHub releases, and DOI/long-term archival sites. If any single location is compromised and replaced, it can be detected via the other mirrors.

## Avoid Overclaiming

Even if the above four layers are implemented, they only improve the supply chain trustworthiness of the finite certificate; they do not automatically elevate the finite-dimensional Weil result to a proof of the RH.
